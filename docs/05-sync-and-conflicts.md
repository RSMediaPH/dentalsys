# 05 — Synchronization design, record ownership and conflict policy

Status: **implemented in Milestone 2** (outbox since Milestone 1). Operator setup: `11-cloud-setup.md`. Tests: `test/sync.test.ts`.

## Principles

1. Network delivery is **at-least-once**. Every receiver is idempotent; repeating a delivery never repeats a business effect.
2. Device clocks are **not** used to order or resolve changes. Ordering uses per-branch sequence numbers assigned by the branch server and cloud-assigned global cursors. Timestamps are kept for display and audit only.
3. Every record has exactly one **owner** (a branch, or the organization via the cloud). Only the owner writes the authoritative version; others hold read-only replicas or submit *requests* the owner accepts.
4. A local business change and its outbox event commit in **the same database transaction** (implemented: `src/domain/outbox.ts`, used by every write).

## Identifiers

| Thing | Format | Generated by |
|---|---|---|
| Record IDs | UUIDv7 | Branch server (offline) |
| Event IDs | UUIDv7 | Branch server, inside the business transaction |
| Branch sequence | integer, strictly increasing per branch (`outbox_events.seq`) | Branch server |
| Node (server) identity | UUID created at install, registered at enrollment | Branch server |
| Patient number | `<BRANCHCODE>-<n>` e.g. `MKT-000042` | Branch server; unique org-wide because branch codes are unique per org |
| Invoice number | `INV-<BRANCHCODE>-<yyyy>-<n>` | Branch server, at issue time |
| Payment number | `PAY-<BRANCHCODE>-<yyyy>-<n>` | Branch server |
| Payment ID | UUID created **when the payment form is opened** and submitted with it | Makes double-clicks and retries idempotent |

## Event envelope (`outbox_events`)

```
id            UUIDv7 (idempotency key at the cloud)
org_id, branch_id, node_id
seq           per-branch monotonically increasing integer
entity_type   'patient' | 'appointment' | 'invoice' | 'payment' | ...
entity_id
op            'created' | 'updated' | 'status_changed' | 'issued' | 'voided' | 'reversed' | ...
entity_version  integer version of the record after this change
base_version    version the editor started from (for conflict detection)
payload       JSON (full new state for small records; facts for append-only records)
schema_version  payload schema version
app_version
created_at    branch server clock (informational)
status        pending | sent | acked | failed
attempts, last_error, acked_at
```

## Upload (branch → cloud)

1. Sync worker reads `pending` events ordered by `seq`, in batches.
2. `POST /sync/v1/events` with the batch, authenticated with the branch node's enrollment credential (mutual identity: node ID + secret; TLS).
3. Cloud, in one Postgres transaction per event: `INSERT … ON CONFLICT (event_id) DO NOTHING`; if inserted, apply to read models. Validates that `org_id`/`branch_id` match the node's enrollment and that the branch owns the `entity_type`. Rejects events with unsupported `schema_version` (returns a typed error; branch marks them `failed`, visible in the UI).
4. Cloud responds with per-event result: `accepted` | `duplicate` (already had it — treated as success) | `rejected:<reason>`.
5. Branch marks `acked` in a durable transaction. If the response is lost, the worker resends; the cloud returns `duplicate`. **Nothing is duplicated.**
6. Gaps: cloud tracks the highest contiguous `seq` per branch, and reports it, so the branch can detect and resend missing events after a crash or restore.

## Download (cloud → branch)

* Cloud assigns each accepted event a global, per-organization **cursor** (monotonic bigint).
* Branch calls `GET /sync/v1/changes?after=<cursor>&limit=500` and applies changes it is entitled to see (shared patients, other branches' summaries, staff/permission changes, catalog/price changes), then stores the new cursor **in the same transaction** as the applied changes. A crash mid-batch re-downloads from the last committed cursor; applying is idempotent (keyed by event ID).

## Versioning and compatibility

* `SYNC_PROTOCOL_VERSION` (integer) is sent on every call. The cloud supports the current and previous version. An unsupported version gets HTTP 426 and the branch shows "Update required — sync paused"; local work continues and events keep queueing (they are not lost).
* Every payload carries `schema_version`; the cloud upgrades older payloads with explicit converters.

## Deletion

Most clinical and financial records are never deleted (void/reverse/amend instead). Where deletion is allowed (e.g. a draft invoice line, a mistaken draft appointment), a **tombstone** event `op='deleted'` is emitted and replicas remove the row but keep the tombstone ID to ignore late updates.

## Attachments (Milestone 3)

Files are content-addressed (SHA-256). Events reference the hash; the file is uploaded separately with resumable chunked upload and verified by checksum before the event is marked complete on the cloud. Download is lazy and checksum-verified.

## Ownership and conflict policy by record type

| Record | Owner | Who may change | Conflict policy |
|---|---|---|---|
| Organization settings, roles, staff memberships | Organization (cloud) | Owner/manager via cloud; local emergency deactivation at branch | Cloud authoritative. Local deactivation is an event that the cloud accepts (safety-first: deactivations always win). |
| Branch profile, hours, chairs, working blocks | Branch | Branch manager at that branch | Single writer, no conflicts. |
| **Patient identity & demographics** | Shared (org) | Any branch with `patient.edit` | Field-level 3-way comparison using `base_version`. Non-overlapping field edits merge automatically. Same field changed differently at two branches → **conflict record** shown to authorized users with both values; record keeps the version that arrived first at the cloud until resolved. No silent last-write-wins. |
| Patient medical alerts / history | Shared (org) | `patient.medical.edit` | Same as demographics; conflicts always require review (safety). |
| Patient merge | Cloud | `patient.merge` | Merge is an explicit event (survivor + merged IDs). Branches redirect merged IDs. Never automatic. |
| **Appointments** | The branch where booked | That branch only | Single writer → no overlap conflicts. Other branches see read-only replicas with freshness. Cross-branch booking requests (later) are proposals the owning branch accepts or rejects. |
| **Invoices, payments, reversals** | Issuing branch | That branch only | Append-only facts; idempotent by event ID and payment ID. Corrections are new events (void, reversal). Paying another branch's invoice offline is not supported. |
| **Clinical notes, charts, treatment plans** (M3) | Branch where created | Recording clinician at that branch | Finalized records immutable; amendments are new linked records preserving original text, author, time, reason. Concurrent drafts → both kept, clinician resolves. Never last-write-wins. |
| **Inventory** (M4) | Branch | That branch | Movement ledger (receipt, consumption, adjustment, dispatch, receipt-of-transfer). Stock = sum of movements. A transfer is two events: dispatch at A, receipt at B; in-transit until B records receipt. |

## Conflict workflow (Milestone 2)

`sync_conflicts` table: entity, field(s), local value, incoming value, versions, detected_at, status (`open|resolved`), resolved_by, resolution. Visible as a count in the header for users with the relevant permission; resolving creates a normal versioned update event.

## Implementation notes (Milestone 2)

* **Cloud database:** PostgreSQL (Supabase in production; PGlite, an in-process PostgreSQL, in tests and local demos). Schema: `src/cloud/migrations/`.
* **Change feed ordering:** uploads for one organization are processed one at a time (`pg_advisory_xact_lock`), so change cursors become visible in order and a reader can never skip a change.
* **Patient conflicts:** the cloud keeps a version per field and which server last changed it. An edit whose `base_cloud_version` is older than a field's version, made by a different server, with a different value, becomes a conflict (kept value + incoming value). Consecutive edits from the same server never conflict with each other.
* **Applying a patient state:** a branch does not overwrite a patient that has local edits still waiting to upload. The cloud sends the merged state after processing them.
* **First connection of an existing branch:** its organization records are queued first, then its full history in the original order (same event IDs). Older events are given their author from the records themselves.
* **Branch-owned records** are claimed by the first event (`entity_owners`, keyed without organization so an ID can never be claimed twice). Later changes from any other branch are rejected and shown on that server's Admin page.
* **Unknown change kinds** stop the download (state "error") instead of being skipped, so a newer cloud never causes silent data loss on an older branch.
* **Not yet:** patient merge workflow, attachment sync (M3), remote access through the cloud, cloud backup copies, compaction of the change feed, cloud-side admin web UI (CLI for now).
